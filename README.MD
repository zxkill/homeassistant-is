# Intersvyaz Doorphone for Home Assistant

[![Open your Home Assistant instance and open a repository inside the Home Assistant Community Store.](https://my.home-assistant.io/badges/hacs_repository.svg)](https://my.home-assistant.io/redirect/hacs_repository/?owner=zxkill&repository=homeassistant-is&category=integration)

Самостоятельная HACS-интеграция для домофонов провайдера **«Интерсвязь»**. Она авторизуется через облачные API провайдера и публикует возможности домофона обычными сущностями, событиями и actions Home Assistant. Никакие внешние ассистенты, боты или отдельные серверы для базовой работы не требуются.

> Интеграция не является официальным продуктом АО «Интерсвязь» и использует облачные API, совместимые с мобильным приложением провайдера. Изменения API со стороны провайдера могут потребовать обновления интеграции.

## Возможности

- авторизация по номеру телефона и коду подтверждения;
- выбор договора, если к номеру привязано несколько адресов;
- автоматическая повторная авторизация через стандартный re-auth Home Assistant;
- перенастройка аккаунта без удаления интеграции;
- баланс и основные данные договора;
- автоматическое обнаружение основных и расшаренных домофонов;
- **отдельное устройство Home Assistant для каждого физического домофона**;
- кнопка открытия каждой доступной двери;
- камера домофона со штатной карточкой Camera;
- автоматическое обновление временных ссылок открытия и снимков;
- локальное распознавание лиц без внешнего облака;
- три режима распознавания: выключено, наблюдение, автооткрытие;
- несколько последовательных совпадений перед автооткрытием;
- EventEntity на каждый домофон;
- сенсор последнего посетителя;
- события для автоматизаций и уведомлений;
- безопасная встроенная диагностика с маскированием credentials и персональных данных;
- подробное логирование для диагностики без намеренного вывода токенов.

## Требования

- Home Assistant **2026.8.0+**;
- доступ Home Assistant к `api.is74.ru` и `td-crm.is74.ru`;
- аккаунт Интерсвязи с доступным домофоном;
- для распознавания лиц отдельные тяжёлые CV-пакеты не нужны: Pillow уже входит в Home Assistant Core, а NumPy ставится штатно как musllinux-совместимая зависимость.

> Начиная с 2.0.7 OpenCV и dlib полностью удалены. Официальный Home Assistant Container/HA OS использует Alpine Linux с musl libc, поэтому manylinux/glibc wheels OpenCV не подходят и установщик пытается собирать OpenCV из исходников. Portable-движок 2.0.7 использует только Pillow + `numpy==2.3.2`; Home Assistant сам закрепляет эту версию NumPy как musllinux-совместимую.

> Распознавание по-прежнему выполняется в отдельном worker-процессе. Даже неожиданная ошибка worker не должна останавливать Home Assistant: облачный API, баланс, камеры и открытие двери продолжают работать.

## Установка

### HACS — рекомендуется

1. Нажмите кнопку в начале README либо добавьте `https://github.com/zxkill/homeassistant-is` в **HACS → Custom repositories → Integration**.
2. Установите **Intersvyaz Doorphone**.
3. Перезапустите Home Assistant.
4. Откройте **Настройки → Устройства и службы → Добавить интеграцию → Intersvyaz Doorphone**.

### Ручная установка

Скопируйте каталог:

```text
custom_components/intersvyaz
```

в:

```text
/config/custom_components/intersvyaz
```

и перезапустите Home Assistant.

### Home Assistant OS / Container / Core

Дополнительных `pip install` вручную делать **не нужно**. Python-зависимости объявлены в `manifest.json`, и Home Assistant устанавливает их в своё окружение при загрузке интеграции. Это одинаковая модель для HA OS, Container и Core.

Если установка requirement не удалась, не устанавливайте библиотеки внутрь работающего контейнера вручную. В 2.0.7 единственная дополнительная dependency — `numpy==2.3.2`; она соответствует package constraints Home Assistant для musllinux.

Если после обновления в журнале остались старые сообщения о `SIGILL` от dlib либо о сборке `opencv-*`, это записи предыдущих 2.0.x. В 2.0.7 ни dlib, ни OpenCV больше не используются.

## Первичная настройка

Мастер попросит:

1. номер телефона;
2. код подтверждения, который сообщает сервис Интерсвязи;
3. договор/адрес — только если доступно несколько вариантов.

После этого интеграция получает список домофонов и создаёт устройства автоматически.

Структура в Home Assistant выглядит примерно так:

```text
Интерсвязь                         ← аккаунт / hub
├── Баланс
├── Профиль
│
├── Домофон — <адрес 1>
│   ├── Открыть дверь
│   ├── Камера домофона
│   ├── Состояние
│   ├── Последний посетитель
│   └── Событие
│
└── Домофон — <адрес 2>
    └── ...
```

## Открытие двери

Самый простой способ — сущность **Button → Открыть дверь** нужного домофона.

Также доступен action `intersvyaz.open_door`. Если `door_uid` не передан, используется основной домофон аккаунта.

```yaml
action: intersvyaz.open_door
data:
  entry_id: YOUR_CONFIG_ENTRY_ID
```

При успешном или неуспешном открытии обновляется EventEntity и публикуется соответствующее событие.

## Камеры

Для каждого домофона, для которого API возвращает видео/снимок, создаётся отдельная сущность `camera`.

Версия 2.0 использует единый `SnapshotManager`: камера, фоновые задачи и распознавание переиспользуют свежий кадр вместо параллельного скачивания одной и той же картинки несколькими независимыми путями.

Если временная ссылка на изображение перестала работать, интеграция один раз обновляет список домофонов/ссылок и повторяет получение кадра.


## Все камеры дома / «Умный двор»

Начиная с **2.0.8** интеграция использует отдельный API видеонаблюдения `cams.is74.ru/api/yard-with-group` и создаёт `camera`-сущности для **всех камер, доступных аккаунту**, а не только для основного домофона.

- snapshot берётся из `MEDIA.SNAPSHOT.LIVE.MAIN`;
- живой просмотр использует `MEDIA.HLS.LIVE.MAIN`;
- камера основного подъезда сопоставляется с существующим устройством домофона, поэтому не создаётся второй дубль устройства;
- камеры других подъездов создаются как отдельные camera-only устройства;
- если cameras API временно недоступен, интеграция продолжает работать и использует старую relay-камеру как fallback;
- временные CDN URL с bearer-токеном хранятся только в памяти и не сохраняются в ConfigEntry/diagnostics.

В настройке **«Камеры фонового анализа»** можно выбрать любую доступную камеру двора для локального распознавания. Автоматическое открытие возможно только для камеры, которая сопоставлена с доступным пользователю домофоном открытия.

## Распознавание лиц

Распознавание полностью локальное. Начиная с 2.0.7 используется переносимый worker на Pillow + NumPy: консервативный face-like detector по цветовым/геометрическим признакам и 128-мерный mirror-invariant descriptor яркости/градиентов. Отдельные модели, OpenCV, `dlib`, `face_recognition` и ручной `pip install` не нужны.

Откройте:

**Настройки → Устройства и службы → Intersvyaz Doorphone → Настроить**.

Доступны:

- **Распознавание и автооткрытие**;
- **Добавить лицо** — выбрать существующего Person Home Assistant и загрузить фотографию;
- **Связать лицо с человеком Home Assistant** — для лиц, добавленных до 2.0.9;
- **Удалить лицо**;
- **Камеры фонового анализа**.

Начиная с **2.0.9** лицо в интеграции является не отдельной «записью с именем», а может быть связано с существующей сущностью `person.*` Home Assistant. В UI при добавлении лица сначала выбирается человек Home Assistant, а его актуальное имя берётся из `friendly_name`. Это позволяет использовать одну общую личность во всём доме: presence/device tracker, автоматизации и распознавание домофона ссылаются на одного и того же Person.

Для регистрации используйте фотографию, где хорошо видно **ровно одно лицо**. Если нужного человека ещё нет в Home Assistant, сначала создайте его в **Настройки → Люди**.

Лица, добавленные в 2.0.7–2.0.8 только по имени, сохраняются. Для них в меню появляется пункт **«Связать лицо с человеком Home Assistant»** — descriptor пересчитывать и фотографию загружать заново не нужно.

### Режимы

**Выключено** — изображения не анализируются.

**Только распознавать** — создаются события и обновляется «Последний посетитель», но интеграция никогда не открывает дверь сама. Это безопасный режим по умолчанию для новых установок.

**Распознавать и автоматически открывать** — после подтверждённого совпадения дверь открывается автоматически.

Для новой установки по умолчанию требуется **3 последовательных совпадения**. Это снижает вероятность открытия по одиночному неудачному кадру.

Параметр `Порог расстояния` — это нормализованная portable cosine distance: **чем меньше значение, тем строже совпадение**. Для нового движка безопасное значение по умолчанию — `0.30`. Значение `match_score`, публикуемое в событиях, вычисляется только как удобный `1 - distance` и **не является статистической вероятностью личности**.

> **Важно о безопасности:** локальное распознавание по снимкам не выполняет liveness/anti-spoof проверку и не может доказать, что перед камерой живой человек, а не качественная фотография/экран. Автооткрытие управляет физическим доступом — включайте его только после оценки этого риска. В режиме `auto_open` интеграция дополнительно требует, чтобы на подтверждающем кадре было **ровно одно лицо**, несколько последовательных совпадений и чтобы истёк cooldown.

### Обновление со старой версии

Descriptors, созданные dlib/OpenCV в версиях до 2.0.7, **не совместимы** с новым portable descriptor. Они намеренно игнорируются, чтобы исключить ложные совпадения; известных людей нужно добавить заново. Новые записи помечаются `face_engine=portable_face_v1`.

При миграции ConfigEntry в schema v4 прежний `auto_open` автоматически переводится в безопасный режим **«Только распознавать»**, порог сбрасывается на `0.30`, а подтверждение — на 3 последовательных совпадения. После повторного добавления лиц сначала проверьте распознавание в режиме наблюдения и только затем, если это действительно нужно, включайте auto-open вручную.

## События

У каждого домофона есть штатная `EventEntity` с типами:

- `face_recognized`;
- `unknown_person`;
- `door_opened`;
- `door_open_failed`.

Для обратной совместимости и YAML-автоматизаций также публикуются события event bus:

- `intersvyaz_face_recognized`;
- `intersvyaz_unknown_person`;
- `intersvyaz_door_opened`;
- `intersvyaz_door_open_failed`.

Пример уведомления о знакомом посетителе:

```yaml
alias: Домофон — знакомый посетитель
triggers:
  - trigger: event
    event_type: intersvyaz_face_recognized
conditions:
  - condition: template
    value_template: "{{ trigger.event.data.confirmed | default(false) }}"
actions:
  - action: persistent_notification.create
    data:
      title: Интерсвязь
      message: >-
        Распознано лицо: {{ trigger.event.data.person }}
        (score {{ trigger.event.data.match_score }})
```

Payload распознавания содержит, в частности: `entry_id`, `door_uid`, `door_name`, `person`, `person_entity_id`, `distance`, `match_score`, `faces_detected`, `streak`, `required_matches`, `confirmed`. Для связанного лица `person_entity_id` содержит, например, `person.aleksei`, а `person` — текущее отображаемое имя этой сущности.

## Actions

### `intersvyaz.open_door`

Открыть основной либо конкретный домофон.

### `intersvyaz.add_known_face`

Добавить лицо программно по `image_url` или `image_base64`. Можно передать `person_entity_id` и связать descriptor с существующим Person Home Assistant; старое поле `name` сохранено для обратной совместимости и пакетных сценариев.

### `intersvyaz.remove_known_face`

Удалить лицо по имени либо по связанному `person_entity_id`.

Для обычного пользователя добавление/удаление лица удобнее делать через UI интеграции.

## Re-auth и перенастройка

Если API сообщает, что mobile credentials истекли или отозваны, coordinator поднимает стандартный `ConfigEntryAuthFailed`. Home Assistant показывает карточку **«Требуется повторная авторизация»** — удалять интеграцию не нужно.

Также доступна **Перенастройка**, которая заново проводит авторизацию и выбор договора, сохраняя ту же ConfigEntry. Интеграция проверяет, что в процессе не был случайно выбран другой аккаунт.

## Диагностика и журнал

В **Настройки → Устройства и службы → Intersvyaz → … → Скачать диагностику** доступен безопасный отчёт.

Из диагностики удаляются/маскируются:

- mobile/CRM tokens и Authorization;
- номер телефона и device ID;
- MAC и адрес;
- временные URL снимков и открытия;
- биометрические descriptors известных лиц.

Для более подробной отладки можно временно добавить в `configuration.yaml`:

```yaml
logger:
  logs:
    custom_components.intersvyaz: debug
```

После диагностики верните обычный уровень логирования: фоновые кадры могут генерировать много `debug`-записей.

## Что делать при проблемах

**Интеграция просит повторный вход** — завершите re-auth через UI. Не редактируйте токены вручную.

**Камера перестала показывать изображение** — дождитесь автоматического обновления ссылки либо перезагрузите интеграцию. Если проблема повторяется, приложите Diagnostics и журнал.

**Распознавание недоступно** — проверьте сообщения `custom_components.intersvyaz.recognition` в журнале. В 2.0.7 OpenCV/dlib не нужны; manifest содержит только `numpy==2.3.2`, а Pillow уже входит в Home Assistant Core. Не устанавливайте пакеты вручную внутрь временного контейнера.

**Дверь не открывается** — проверьте, что интеграция не находится в состоянии re-auth и что кнопка относится к нужному физическому домофону.

## Обновление

Перед переходом на 2.0 рекомендуется сделать резервную копию конфигурации Home Assistant.

При обновлении через HACS:

1. обновите интеграцию;
2. перезапустите Home Assistant;
3. убедитесь, что аккаунт, домофоны, камеры и кнопки появились;
4. проверьте настройки распознавания;
5. только после этого тестируйте автооткрытие.

## Разработка

Код 2.0 разделён по ответственности:

```text
custom_components/intersvyaz/
├── api.py                 # высокоуровневые операции облачного API
├── api_models.py          # типизированные модели/парсинг ответов
├── api_errors.py          # доменные API/auth/network ошибки
├── api_transport.py       # HTTP, timeout и безопасный request context
├── config_flow.py         # подключение / reauth / reconfigure
├── options_flow.py        # пользовательские настройки
├── coordinator.py         # профиль и баланс
├── runtime.py             # типизированный ConfigEntry.runtime_data
├── door_manager.py        # обнаружение/обновление/открытие домофонов
├── snapshot.py            # единая загрузка и кеш кадров
├── recognition/           # изолированный portable Pillow/NumPy engine
├── face_manager.py        # база лиц и политика recognition/auto-open
├── events.py              # событийный слой
├── event.py               # EventEntity
├── camera.py
├── button.py
├── sensor.py
├── services.py
├── diagnostics.py
└── security.py            # единое маскирование секретов
```

CI проверяет Python syntax, metadata/tests, HACS validation и hassfest.

## Безопасность и приватность

Не публикуйте `.storage/core.config_entries`, debug-логи старых версий и сырые ответы API: они могут содержать credentials и персональные данные. Версия 2.0 не выводит полные door UID/MAC в журнал; для корреляции используется короткий необратимый hash. Значения ответов API в диагностических debug-summary тоже не печатаются — только структура ответа.

База известных лиц хранит локальные **128-мерные биометрические descriptors** в options ConfigEntry Home Assistant. Они не отправляются во внешний сервис распознавания, но попадают в резервные копии Home Assistant вместе с конфигурацией. Удаление лица убирает его из текущей ConfigEntry, однако старые резервные копии могут по-прежнему содержать descriptor. Диагностический отчёт descriptors не включает.

Автооткрытие не является системой контроля доступа с защитой от предъявления фотографии: локальное сопоставление лица в статичном кадре не содержит liveness/anti-spoof механизма. Для сценариев с повышенными требованиями к безопасности используйте режим `observe` и отдельное подтверждение через автоматизацию Home Assistant.

Если вы обнаружили утечку credentials или персональных данных в диагностике/журнале этой версии, создайте issue **без самого секрета** и опишите место, где он появился.
